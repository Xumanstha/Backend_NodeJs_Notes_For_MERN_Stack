# MongoDB — Notes

## 1. What is MongoDB?

MongoDB is a **NoSQL, document-oriented database** — instead of storing data in rigid tables and rows (like traditional SQL databases), it stores data as flexible, JSON-like documents.

Why it pairs naturally with Node.js/Express: JavaScript objects and MongoDB documents look almost identical, so data flows between your app and database with very little translation.

```js
// A JavaScript object...
const user = { name: "Alice", age: 25, roles: ["admin"] };

// ...looks almost exactly like a MongoDB document
{ "name": "Alice", "age": 25, "roles": ["admin"] }
```

---

## 2. NoSQL

"NoSQL" means **"not only SQL"** — a broad category of databases that don't use the traditional relational (table-based) model.

| | SQL (Relational) | NoSQL (e.g. MongoDB) |
|---|---|---|
| Structure | Tables with fixed columns | Flexible documents |
| Schema | Rigid — defined upfront | Flexible — documents in the same collection can have different fields |
| Relationships | Handled via joins across tables | Handled via embedding or references |
| Examples | MySQL, PostgreSQL | MongoDB, Redis, Cassandra |
| Best for | Structured data, complex relationships, strict consistency | Rapidly evolving data, large-scale/unstructured data, flexible schemas |

MongoDB's flexibility is great for fast-moving projects, but it also means **you** need to be more disciplined about data consistency, since the database won't enforce a strict schema by default.

---

## 3. Database

The top-level container in MongoDB — a single MongoDB server can host multiple databases, each isolated from the others.

```js
use myAppDB
```
This switches to (or creates, if it doesn't exist yet) a database called `myAppDB`. A database holds multiple **collections** (explained next), similarly to how a SQL database holds multiple tables.

---

## 4. Collection

A collection is a **group of related documents** — roughly equivalent to a "table" in SQL, but without a fixed structure.

```js
db.createCollection("users")
```

- A `users` collection might hold many user documents.
- Unlike SQL tables, documents within the same collection **don't need to have the same fields**. This is powerful but also means your application code has to handle inconsistent data carefully.

---

## 5. Document

A document is a **single record** in MongoDB — the equivalent of a "row" in SQL — stored in a JSON-like format.

```js
{
  "_id": "64fabc123456789",
  "name": "Alice",
  "email": "alice@example.com",
  "age": 25,
  "roles": ["admin", "editor"],
  "address": {
    "city": "Kathmandu",
    "zip": "44600"
  }
}
```

Key characteristics:
- Fields can hold strings, numbers, booleans, arrays, dates, or even **nested documents** (like `address` above).
- Documents in the same collection can have different shapes/fields (flexible schema).

---

## 6. `_id`

Every document has a unique `_id` field, automatically generated by MongoDB unless you supply your own.

```js
"_id": ObjectId("64fabc123456789")
```

- Acts as the **primary key** — guaranteed unique within a collection.
- Generated as an `ObjectId` — a special 12-byte identifier that's efficient to generate and roughly sortable by creation time.
- You can query by it directly:
```js
db.users.findOne({ _id: ObjectId("64fabc123456789") })
```

---

## 7. BSON

MongoDB doesn't actually store data as plain JSON text — it stores it as **BSON** ("Binary JSON").

Why BSON instead of plain JSON:
- **Faster to parse and traverse** than text-based JSON.
- **More data types** — supports things JSON doesn't have natively, like `Date`, `ObjectId`, and binary data.
- **More compact** for storage and network transfer.

You don't usually interact with BSON directly — you write queries using normal JSON-like syntax, and MongoDB handles the BSON conversion internally.

## 8. CRUD Operations

CRUD = **Create, Read, Update, Delete** — the four basic operations on data.

| Operation | MongoDB Method |
|---|---|
| Create | `insertOne()`, `insertMany()` |
| Read | `find()`, `findOne()` |
| Update | `updateOne()`, `updateMany()` |
| Delete | `deleteOne()`, `deleteMany()` |

**Create:**
```js
db.users.insertOne({ name: "Alice", age: 25 });
db.users.insertMany([
  { name: "Bob", age: 30 },
  { name: "Carol", age: 28 }
]);
```

**Read:**
```js
db.users.find();                     // all documents
db.users.findOne({ name: "Alice" }); // first match
db.users.find({ age: { $gt: 25 } }); // filtered
```

**Update:**
```js
db.users.updateOne(
  { name: "Alice" },
  { $set: { age: 26 } }
);

db.users.updateMany(
  { age: { $lt: 30 } },
  { $set: { status: "young" } }
);
```

**Delete:**
```js
db.users.deleteOne({ name: "Alice" });
db.users.deleteMany({ age: { $lt: 18 } });
```

---

## 9. MongoDB Queries

A query is an object describing **which documents to match** — you pass a "filter" object to methods like `find()`.

```js
// Match exactly
db.users.find({ name: "Alice" });

// Match nested field
db.users.find({ "address.city": "Kathmandu" });

// Match with multiple conditions (implicit AND)
db.users.find({ age: 25, status: "active" });

// Sort, limit, skip (chained onto find)
db.users.find().sort({ age: -1 }).limit(10).skip(5);
```

- `{}` (empty filter) = match all documents.
- `.sort({ field: 1 })` = ascending, `-1` = descending.
- `.limit(n)` = cap the number of results.
- `.skip(n)` = skip the first `n` results (used for pagination).

---

## 10. MongoDB Operators

Operators (prefixed with `$`) let you build more expressive queries and updates beyond simple equality.

**Query/comparison operators:**
| Operator | Meaning | Example |
|---|---|---|
| `$eq` | equal to | `{ age: { $eq: 25 } }` |
| `$ne` | not equal to | `{ age: { $ne: 25 } }` |
| `$gt` / `$gte` | greater than / or equal | `{ age: { $gt: 18 } }` |
| `$lt` / `$lte` | less than / or equal | `{ age: { $lt: 65 } }` |
| `$in` | value in a list | `{ role: { $in: ["admin", "editor"] } }` |
| `$nin` | value not in a list | `{ role: { $nin: ["banned"] } }` |

**Logical operators:**
```js
db.users.find({ $and: [{ age: { $gt: 18 } }, { status: "active" }] });
db.users.find({ $or: [{ role: "admin" }, { role: "editor" }] });
```

**Update operators:**
| Operator | Meaning | Example |
|---|---|---|
| `$set` | set/update a field's value | `{ $set: { age: 26 } }` |
| `$unset` | remove a field | `{ $unset: { age: "" } }` |
| `$inc` | increment a numeric field | `{ $inc: { age: 1 } }` |
| `$push` | add an item to an array | `{ $push: { roles: "editor" } }` |
| `$pull` | remove an item from an array | `{ $pull: { roles: "editor" } }` |

Example combining a query filter with an update operator:
```js
db.users.updateOne(
  { name: "Alice" },
  { $inc: { age: 1 }, $push: { roles: "manager" } }
);
```

## 11. Relationships

Even though MongoDB is non-relational, real apps still need to represent connections between data — e.g., a user who has many posts. MongoDB gives you two main strategies:

### Embedded Documents
Store related data **directly inside** the parent document.

```js
{
  "_id": "user123",
  "name": "Alice",
  "posts": [
    { "title": "My first post", "content": "Hello world!" },
    { "title": "Another post", "content": "..." }
  ]
}
```

### References
Store just the **`_id`** of the related document, and look it up separately (similar to a foreign key in SQL).

```js
// users collection
{ "_id": "user123", "name": "Alice" }

// posts collection
{ "_id": "post1", "title": "My first post", "authorId": "user123" }
```

To fetch related data, you'd either query separately or use `$lookup` (MongoDB's version of a SQL join, used in aggregation pipelines).

---

## 12. Embedded Documents vs References

Choosing between them is one of the most important MongoDB design decisions.

| | Embedded Documents | References |
|---|---|---|
| **Data location** | Nested inside the parent document | Stored in a separate collection, linked by `_id` |
| **Read performance** | Fast — one query gets everything | Slower — may need multiple queries or a `$lookup` |
| **Best for** | Data that's always accessed together, doesn't grow unbounded (e.g., an address inside a user) | Data that's shared, reused, or grows large/unbounded (e.g., a user's posts, comments) |
| **Document size limit** | MongoDB documents are capped at 16MB — large embedded arrays can hit this | Not affected by parent document size |
| **Data duplication** | Can lead to duplication if the same data appears in multiple places | Avoids duplication (single source of truth) |

**Rule of thumb:**
- If related data is small, bounded, and mostly read together → **embed** it.
- If related data is large, grows over time, or is shared across multiple parents → **reference** it.

Example: a user's `address` is a good candidate for embedding (small, tightly coupled). A user's `posts` (potentially thousands over time) is a better candidate for referencing.

## 13. Indexes

An index is a special data structure that lets MongoDB find documents **without scanning the entire collection** — dramatically speeding up queries, similar to an index in the back of a book.

```js
db.users.createIndex({ email: 1 }); // 1 = ascending, -1 = descending
```

Without an index, `db.users.find({ email: "alice@example.com" })` would scan every document in the collection (a "collection scan"). With an index on `email`, MongoDB can jump straight to matching documents.

**Common index types:**
```js
db.users.createIndex({ email: 1 }, { unique: true }); // unique index — prevents duplicate emails
db.users.createIndex({ name: 1, age: -1 });            // compound index — multiple fields
db.posts.createIndex({ title: "text" });                // text index — enables text search
```

**Trade-offs:**
- Indexes speed up **reads** (queries).
- But they slow down **writes** slightly (every insert/update must also update the index) and consume extra storage.
- Every collection automatically has an index on `_id` by default.

**Check what indexes exist:**
```js
db.users.getIndexes();
```

---

## Quick Recap

- **MongoDB** = NoSQL, document-oriented database that stores flexible JSON-like data
- **Database → Collection → Document** = the storage hierarchy (like Database → Table → Row in SQL)
- **`_id`** = auto-generated unique identifier for every document
- **BSON** = the efficient binary format MongoDB actually stores data in
- **CRUD** = `insertOne/Many`, `find/findOne`, `updateOne/Many`, `deleteOne/Many`
- **Operators** (`$gt`, `$set`, `$push`, etc.) = build powerful queries and updates
- **Relationships** = handled via **embedding** (nested data) or **references** (linked by `_id`)
- **Indexes** = speed up queries at the cost of extra storage and slightly slower writes
